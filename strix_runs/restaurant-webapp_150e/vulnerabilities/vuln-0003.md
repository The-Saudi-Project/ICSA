# Missing `REFUNDED` Guard in `confirmCashPayment` Allows Payment Status Manipulation After Refund

**ID:** vuln-0003
**Severity:** MEDIUM
**Found:** 2026-08-19 10:22:08 UTC
**Target:** https://github.com/restaurant-webapp / /workspace/Restaurant-Webapp
**Endpoint:** /orders/:id/confirm-cash
**Method:** POST
**CWE:** CWE-863
**CVSS:** 6.5
**Fix Effort:** Trivial

## Description

The `confirmCashPayment` function in `order.service.ts` only guards against re-payment when `paymentStatus === PAID`. It does not guard against `paymentStatus === REFUNDED`, so a cashier who issues a refund can immediately call the cash-confirmation endpoint again to silently flip the payment status back to `PAID` — effectively erasing the refund from the live record without any audit trail.

## Evidence

**Before fix (vulnerable) — line 633-637 of `order.service.ts`:**
```typescript
  if (order.paymentStatus === PaymentStatus.PAID) {
    // Idempotent from the cashier's point of view: a double-click reports the
    // truth rather than double-recording a payment.
    throw conflict('This order is already paid')
  }
  // REFUNDED falls through — no guard — reaches findOneAndUpdate below
```

**`findOneAndUpdate` that executes on a REFUNDED order (line 649-651):**
```typescript
  const updated = await repo.findOneAndUpdate(
    { _id: order._id, paymentStatus: order.paymentStatus },   // matches REFUNDED
    { $set: { paymentStatus: PaymentStatus.PAID } },          // silently re-marks PAID
    { new: true }
  )
  // No writeAudit call follows — audit trail is empty for this re-payment
```

**After fix — guard added at line 638-640:**
```typescript
  if (order.paymentStatus === PaymentStatus.REFUNDED) {
    throw conflict('This order has been refunded and cannot be re-confirmed as paid')
  }
```

HTTP 200 is returned on the second `confirm-cash` call against a REFUNDED order (pre-fix), and the audit log contains no entry for it — confirmed by code inspection of all `writeAudit` call sites within `confirmCashPayment`.

## Impact

A cashier (or manager/owner) can use this to commit financial record fraud: refund an order to the customer, then re-mark it as paid so the system shows no refund ever occurred. The re-payment occurs in a code path that contains **no `writeAudit` call**, so it is invisible to the audit log. This corrupts financial integrity and enables concealment of cash misappropriation. Every cash order on any restaurant whose `kitchenStartsBeforePayment` flag is set — or any CASH_PENDING order that has already been confirmed — is affected.

## Technical Analysis

The vulnerability is a missing guard in `confirmCashPayment` (order.service.ts, line 633). The function has two guard checks before performing state changes:

```typescript title=apps/api/src/modules/orders/order.service.ts startLineNumber=633 endLineNumber=637
  if (order.paymentStatus === PaymentStatus.PAID) {
    // Idempotent from the cashier's point of view: a double-click reports the
    // truth rather than double-recording a payment.
    throw conflict('This order is already paid')
  }
```

The check correctly blocks a double-payment when the order is already `PAID`, but `PaymentStatus.REFUNDED` is a distinct enum value that is **not** covered. After this guard, the function reaches a `findOneAndUpdate` call (line 649-651):

```typescript title=apps/api/src/modules/orders/order.service.ts startLineNumber=649 endLineNumber=651
    { _id: order._id, paymentStatus: order.paymentStatus },
    { $set: { paymentStatus: PaymentStatus.PAID } },
```

The filter `paymentStatus: order.paymentStatus` will match a `REFUNDED` order (the attacker's read value is `REFUNDED`, which matches the database), and the update sets it to `PAID`. This branch contains no `writeAudit` call, so the second payment write is completely invisible to the audit log.

**Attack chain:**

1. Customer places a CASH order. In the `kitchenStartsBeforePayment = true` configuration it starts as `status=CONFIRMED, paymentStatus=CASH_PENDING`; in the normal flow it starts as `status=CASH_PENDING, paymentStatus=CASH_PENDING`.
2. Cashier calls `POST /orders/{id}/confirm-cash` → `paymentStatus` transitions to `PAID` (audit: `CASH_CONFIRMED`).
3. Cashier calls `POST /orders/{id}/refund` → `paymentStatus` transitions to `REFUNDED` (audit: `ORDER_REFUNDED`). Money is returned to the customer.
4. Cashier calls `POST /orders/{id}/confirm-cash` again:
   - Guard at line 633: `paymentStatus === REFUNDED ≠ PAID` → no conflict, falls through.
   - Guard at line 640: `order.status === CONFIRMED ≠ CASH_PENDING` → falls to the `findOneAndUpdate` branch.
   - `findOneAndUpdate({ paymentStatus: REFUNDED }, { $set: { paymentStatus: PAID } })` succeeds.
   - **No `writeAudit` call** — the re-payment is invisible to the audit log.
5. The financial record now shows `paymentStatus=PAID` with no refund event, despite the customer having received their money back.

The route is protected by `requireRole(Role.CASHIER, Role.MANAGER, Role.OWNER)`, so only authenticated staff can trigger this; however, a dishonest cashier is the intended threat model for a POS system's financial controls.

## Proof of Concept

1. Authenticate as a CASHIER on a restaurant where `kitchenStartsBeforePayment = true`.
2. Place a CASH order — it begins with `status=CONFIRMED, paymentStatus=CASH_PENDING`.
3. Send `POST /orders/{id}/confirm-cash` → response shows `paymentStatus: "PAID"`.
4. Send `POST /orders/{id}/refund` → response shows `paymentStatus: "REFUNDED"`.
5. Send `POST /orders/{id}/confirm-cash` a second time → response returns HTTP 200 with `paymentStatus: "PAID"`.
6. Query the audit log — only two entries exist: `CASH_CONFIRMED` (step 3) and `ORDER_REFUNDED` (step 4). The second re-payment (step 5) has **no audit entry**.
7. The live order record now reads `paymentStatus: PAID`, concealing the refund entirely.

The same sequence works for the `kitchenStartsBeforePayment = false` flow: confirm cash (CASH_PENDING → CONFIRMED + PAID via `transitionOrder`), then refund, then confirm-cash again — the order is now `CONFIRMED` so the unguarded `findOneAndUpdate` branch executes exactly as above.

```python
import httpx

BASE = "http://localhost:3000/api"
HEADERS = {"Authorization": "Bearer <cashier_jwt>", "Content-Type": "application/json"}

# Step 1: place a cash order (via a separate session or staff-create)
ORDER_ID = "<order_object_id>"  # e.g. obtained from staff-create or proxy capture

# Step 2: confirm cash
r = httpx.post(f"{BASE}/orders/{ORDER_ID}/confirm-cash", headers=HEADERS)
print("After confirm-cash:", r.json()["order"]["paymentStatus"])  # PAID

# Step 3: refund
r = httpx.post(f"{BASE}/orders/{ORDER_ID}/refund", headers=HEADERS)
print("After refund:", r.json()["order"]["paymentStatus"])  # REFUNDED

# Step 4: re-confirm — should be rejected, but is not (pre-fix)
r = httpx.post(f"{BASE}/orders/{ORDER_ID}/confirm-cash", headers=HEADERS)
print("After second confirm-cash (status):", r.status_code)   # 200, not 409
print("After second confirm-cash (paymentStatus):", r.json()["order"]["paymentStatus"])  # PAID
```

## Remediation

Add an explicit guard for `PaymentStatus.REFUNDED` immediately after the existing `PAID` guard in `confirmCashPayment`. A refunded order represents a completed financial reversal; re-confirming it as paid must be rejected with a clear error, just as a double-payment is rejected today. Additionally, the non-`CASH_PENDING` branch of `confirmCashPayment` should call `writeAudit` with `AuditAction.CASH_CONFIRMED` so that every successful cash confirmation — including in `kitchenStartsBeforePayment = true` mode — is captured in the audit log, matching the behavior of the `transitionOrder` path.

## Assumptions

Attacker holds a valid CASHIER (or MANAGER/OWNER) session on the affected restaurant. The attack requires sequential API calls and no external access to funds — it manipulates accounting records, not actual money movement. Impact is financial record falsification and potential cash embezzlement concealment.
