# Missing Maximum Length Constraint on Menu Item Search Query Parameter

**ID:** vuln-0002
**Severity:** MEDIUM
**Found:** 2026-08-19 10:18:47 UTC
**Target:** Restaurant Webapp — `apps/api/src/modules/menu/menu.routes.ts`, `apps/api/src/modules/menu/menu.service.ts`
**Endpoint:** /api/v1/app/menu/items/search
**Method:** GET
**CWE:** CWE-400
**CVSS:** 4.3
**Fix Effort:** Trivial

## Description

The staff-facing menu search endpoint accepts a query string parameter `q` with no upper-length bound. The application compiles this unbounded input into a JavaScript `RegExp` object before passing it to MongoDB, enabling authenticated staff members to submit arbitrarily large strings that cause disproportionate CPU and memory consumption on both the API server and the database node.

## Evidence

The route schema in `menu.routes.ts` (line ~61) defines:
```typescript
const searchSchema = z.object({ q: z.string().min(1) })
```
No `.max()` constraint is present. The `searchItems` function in `menu.service.ts` performs `new RegExp(safeQuery, 'i')` on the full untruncated string, then issues a four-field `$or: [...$regex]` query to MongoDB without limiting the pattern size.

## Impact

An authenticated staff member (any role that can access the menu — WAITER, CASHIER, KITCHEN, MANAGER, OWNER) can submit a very long query string (e.g., hundreds of kilobytes) to the search endpoint. The API server executes `new RegExp(largeString, 'i')` and then issues a MongoDB `$regex` query against four indexed fields. This can cause elevated CPU usage, slow query execution, or service degradation for other users of the same API process. The attack requires valid staff credentials.

## Technical Analysis

In `menu.routes.ts`, the query schema is:

```typescript title=apps/api/src/modules/menu/menu.routes.ts startLineNumber=61 endLineNumber=62
const searchSchema = z.object({ q: z.string().min(1) })
```

No `.max()` is applied. The validated value is passed to `menuService.searchItems()`:

```typescript title=apps/api/src/modules/menu/menu.service.ts startLineNumber=235 endLineNumber=244
export async function searchItems(query: string): Promise<MenuItemView[]> {
  const repo = tenantRepo(MenuItemModel)
  const safeQuery = query.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')
  const regex = new RegExp(safeQuery, 'i')

  const items = await repo.find({
    $or: [
      { 'name.en': { $regex: regex } },
      { 'name.ar': { $regex: regex } },
      { 'description.en': { $regex: regex } },
      { 'description.ar': { $regex: regex } }
    ]
  }, { limit: 50 })

  return items.map(toItemView)
}
```

The metacharacter escaping neutralizes catastrophic-backtracking patterns (the `[.*+?^${}()|[\]\\]` substitution is correct), but there is no bound on the resulting string length before it is compiled into a `RegExp`. A 500 KB query string becomes a 500 KB regex pattern object in memory and a 500 KB BSON `$regex` clause sent to MongoDB. The global JSON body limit (`BODY_LIMIT=100kb`) only applies to request bodies — query strings bypass it. The general `apiRateLimit` (300 req/min) limits how many such requests can be made but does not restrict the size of each individual request.

## Proof of Concept

1. Authenticate as any staff member (WAITER or higher role) and obtain a valid access token.
2. Construct a GET request to `/api/v1/app/menu/items/search` with a `q` parameter containing a very long string (e.g., 100,000 repetitions of `a`).
3. Observe that the server processes the request without rejecting it for size.
4. Monitor server CPU and response latency; both increase proportionally to the query string length.
5. Repeat at the rate limit (300/min) to sustain elevated load.

```python
import requests

API_BASE = "http://localhost:4000/api/v1"
TOKEN = "<valid staff JWT>"

long_query = "a" * 100_000

resp = requests.get(
    f"{API_BASE}/app/menu/items/search",
    params={"q": long_query},
    headers={"Authorization": f"Bearer {TOKEN}"},
    timeout=60,
)
print(f"Status: {resp.status_code}, response time: {resp.elapsed.total_seconds():.2f}s")
```

## Code Analysis

**Location 1:** `apps/api/src/modules/menu/menu.routes.ts` (lines 61-62)
  Add max() constraint to search schema
  ```
  const searchSchema = z.object({ q: z.string().min(1) })
  ```

  **Suggested Fix:**
```diff
- const searchSchema = z.object({ q: z.string().min(1) })
+ const searchSchema = z.object({ q: z.string().min(1).max(200) })
```

## Remediation

Add a maximum length constraint to the search schema so that the query string is rejected at the validation layer before any regex or database operation is performed. A limit of 200 characters is consistent with the `reason` field in transition schemas and is more than sufficient for real menu searches. Additionally, consider enforcing a maximum regex pattern size at the `searchItems` service level as defence-in-depth.

## Assumptions

Assumes the attacker holds valid staff credentials for any role that has access to the menu endpoint (WAITER, CASHIER, KITCHEN, MANAGER, or OWNER).
