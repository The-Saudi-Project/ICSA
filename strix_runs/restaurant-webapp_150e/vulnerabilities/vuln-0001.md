# Sensitive Credentials Stored in Plaintext `.env` File

**ID:** vuln-0001
**Severity:** CRITICAL
**Found:** 2026-08-19 10:18:02 UTC
**Target:** Restaurant Webapp — `/workspace/Restaurant-Webapp/apps/api/.env`
**Endpoint:** apps/api/.env
**CWE:** CWE-798
**CVSS:** 10.0
**Fix Effort:** High

## Description

The repository's API application stores real, active service credentials in a plaintext `.env` file located at `apps/api/.env`. This file contains production-grade secrets — including a MongoDB Atlas connection string with embedded username and password, Cloudinary API key and secret, JWT signing secrets, AES-256 encryption keys, and the platform administrator's email address — with no encryption or secret-management protection.

The following secrets are present in `apps/api/.env` (values truncated for the report):

The `.gitignore` at the repository root confirms `*.env` and `.env.*` are excluded from version control, confirming these are active development credentials, not placeholders.

## Impact

An attacker who gains read access to the repository workspace (e.g., through a compromised developer machine, an accidental commit, a CI/CD misconfiguration, or repository hosting exposure) obtains all of the following without additional effort: full read/write access to the MongoDB Atlas database containing all restaurant orders, menus, staff accounts, and customer session data; the ability to forge arbitrary JWT access tokens for any user role (including PLATFORM_ADMIN) using the exposed `JWT_ACCESS_SECRET`; the ability to forge customer table-session tokens using the exposed `TABLE_SESSION_SECRET`; the ability to decrypt all stored NFC table tokens using the exposed `TABLE_TOKEN_KEY`; and full control over the Cloudinary image storage account. The platform admin email address is also disclosed, facilitating targeted phishing and credential-stuffing attacks.

## Technical Analysis

The file `apps/api/.env` contains the following active credentials in plaintext:

```
MONGODB_URI=mongodb+srv://shamalkhalidnp_db_user:<password>@jazeera-tech.dcnnewe.mongodb.net/restaurant_dev
JWT_ACCESS_SECRET=<64-byte hex string>
TABLE_SESSION_SECRET=<54-char string>
TABLE_TOKEN_KEY=<base64-encoded 32-byte AES key>
IP_HASH_SALT=<base64 salt>
CLOUDINARY_CLOUD_NAME=jrtvkyhp
CLOUDINARY_API_KEY=177313156823726
CLOUDINARY_API_SECRET=<secret>
PLATFORM_ADMIN_EMAIL=shamalkhalidnp@gmail.com
```

While `apps/api/.env` is correctly listed in `.gitignore`, that protection only prevents **accidental git commits** — it does not protect against:
- Developers sharing the file via other channels (Slack, email, cloud storage)
- CI/CD pipelines that copy the entire workspace
- Attackers who gain filesystem access to a developer machine or build server
- Secrets being captured by container image layers or artifact archives

The critical risk is `JWT_ACCESS_SECRET`: because the API pins tokens to `HS256` (symmetric HMAC), any party holding this secret can forge a valid access token for any `sub` (user ID), any `role` (including `PLATFORM_ADMIN`), and any `rid` (tenant). A forged PLATFORM_ADMIN token bypasses all RBAC, grants cross-tenant read/write access, and enables full data exfiltration.

Similarly, `TABLE_SESSION_SECRET` allows forging customer session tokens without scanning an NFC tag, granting unauthorized access to any restaurant's ordering surface. `TABLE_TOKEN_KEY` (AES-256-GCM) allows decrypting every stored NFC table token from the database.

Additionally, the commented-out line `# PLATFORM_ADMIN_PASSWORD=Plh52Nb23G0L2d&wefP98Jyh67` suggests the password has been used and may still be active, disclosing it to anyone reading the file.

## Proof of Concept

1. Obtain the file `apps/api/.env` from the repository workspace.
2. Extract the value of `JWT_ACCESS_SECRET` from the file.
3. Use a JWT library to craft a token with `alg=HS256`, `iss=rw-api`, `aud=rw-staff`, `role=PLATFORM_ADMIN`, `sub=<any valid user ObjectId>`, `rid=null`, `tv=0`, and a far-future expiry.
4. Sign the token with the extracted `JWT_ACCESS_SECRET`.
5. Issue an HTTP request to any platform-admin-protected endpoint (e.g., `GET /api/v1/platform/restaurants`) with `Authorization: Bearer <forged_token>`.
6. Observe that the server accepts the token and returns all restaurant data.

```python
import jwt
import time

# Extracted from apps/api/.env
JWT_ACCESS_SECRET = "<value from JWT_ACCESS_SECRET in .env>"

payload = {
    "sub": "000000000000000000000001",  # any MongoDB ObjectId
    "rid": None,
    "role": "PLATFORM_ADMIN",
    "tv": 0,
    "iss": "rw-api",
    "aud": "rw-staff",
    "iat": int(time.time()),
    "exp": int(time.time()) + 3600,
    "jti": "forged-token",
}

forged = jwt.encode(payload, JWT_ACCESS_SECRET, algorithm="HS256")
print("Forged token:", forged)

# Use in request:
# curl -H "Authorization: Bearer <forged_token>" https://<api-host>/api/v1/platform/restaurants
```

## Remediation

**Immediate actions:**
1. Rotate every credential present in the `.env` file: MongoDB Atlas password, JWT_ACCESS_SECRET, TABLE_SESSION_SECRET, TABLE_TOKEN_KEY, IP_HASH_SALT, and all Cloudinary credentials. Treat all as compromised.
2. Change the platform administrator password if `Plh52Nb23G0L2d&wefP98Jyh67` (or a derivative) remains active.
3. Audit MongoDB Atlas access logs for unexpected read/write activity from the leaked credentials.

**Process improvements:**
4. Adopt a secrets manager (e.g., HashiCorp Vault, AWS Secrets Manager, Doppler) or OS-level keychain. Never store production secrets in `.env` files, even in ignored files.
5. Add a pre-commit hook using `gitleaks` or `trufflehog` to prevent accidental secret commits.
6. For development, use short-lived, scope-limited secrets or mock credentials — never real Atlas/Cloudinary credentials in local `.env` files.
7. Rotate JWT and session secrets automatically on a schedule; configure the server to accept two concurrent secrets during the rotation window.
8. Add a CI/CD secrets-scanning step that fails the pipeline if any secret pattern is detected in committed files or environment exports.

## Assumptions

Assumes an attacker has gained read access to the developer workspace or the file has been inadvertently shared. The JWT forgery PoC is conditional on the `JWT_ACCESS_SECRET` remaining unchanged from what is in the file.
